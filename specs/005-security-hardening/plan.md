# Implementation Plan: Security Hardening

**Date**: 2026-06-03
**Spec**: [specs/005-security-hardening/spec.md](spec.md)

## Summary

Pure hardening pass: fixes 7 gosec findings (G404, G108, G115 × 2, G118, G104 × 2) and
18 CVEs in the Go standard library. All changes are confined to four existing source files
and three config/CI files — no new packages, no schema migrations, no new HTTP endpoints,
and no new dependencies. The Go toolchain is bumped from 1.25.0 to 1.25.10 to clear all
CVEs. Both the static security scanner (gosec) and the vulnerability scanner (govulncheck)
are added to the Makefile and CI pipeline so that regressions fail the build automatically.

## Technical Design

### US1 — Replace `math/rand` with `crypto/rand` (G404)

**File**: `internal/domain/retry.go`

**Decision**: Use `crypto/rand.Read` directly rather than `math/rand/v2`.

`math/rand/v2` is seeded automatically with a cryptographically random value but is a
PRNG, not a CSPRNG — its output can in principle be predicted from prior outputs. FR-001
requires "a cryptographically secure source", meaning outputs must be drawn from a
hardware-entropy-backed generator. Only `crypto/rand` satisfies this requirement.
`math/rand/v2` would suppress gosec G404 but would not comply with FR-001.

**Change**:
- Replace `import "math/rand"` with `import (crand "crypto/rand"; "encoding/binary")`.
- Change `applyJitter(base time.Duration) time.Duration` →
  `applyJitter(base time.Duration) (time.Duration, error)`:
  read 8 bytes from `crand.Read`, interpret as `uint64` via `binary.BigEndian.Uint64`,
  apply modulo and shift using the chain below to produce a delta centred on zero, add to
  base:
  ```go
  raw := binary.BigEndian.Uint64(b[:])
  delta := int64(raw%uint64(span)) - span/2  // result in [-span/2, span/2)
  return base + time.Duration(delta), nil
  ```
  Using `uint64` for the modulo avoids the negative-remainder behaviour that `int64 % int64`
  would produce when bit 63 of the random bytes is set (Go's `%` returns a non-positive
  result for negative dividends). The cast to `int64` after the modulo is safe because
  `raw%uint64(span) < uint64(span) <= int64(base)*30/100 <= MaxInt64`.
- `crypto/rand.Read` never returns a non-nil error in Go ≥ 1.20 (documented stdlib
  guarantee). The error is still captured and returned to satisfy FR-007.
- Change `Delay(n int) time.Duration` → `Delay(n int) (time.Duration, error)`: forward
  the error from `applyJitter`.
- **Caller update** (`internal/delivery/worker.go:188`): change
  `delay := domain.Delay(…)` to `delay, err := domain.Delay(…)`. On non-nil error, log
  it and fall back to the base schedule duration without jitter using a new unexported
  `baseDelay(n int) time.Duration` helper in `retry.go`. This keeps retry behaviour
  correct even in the (impossible on Go 1.25) case of a crypto/rand failure, while
  surfacing the failure to the caller rather than silently discarding it.

### US2 — Remove pprof import and fix G118 (G108, G118)

**File**: `cmd/webhookd/main.go`

**G108 fix**: Delete `_ "net/http/pprof"` at line 8. This one-line change removes all
pprof handler registrations from `http.DefaultServeMux`.

**G118 + dead code removal**: Remove the `startPprofServer` function entirely, along with
the `--pprof-addr` flag declarations and their call sites in all three subcommands
(`runAPI`, `runWorker`, `runScheduler`). With the import gone, `startPprofServer` served
only an empty mux; removing it also eliminates the G118 finding (the goroutine using
`context.Background()` inside `startPprofServer` disappears with the function).

The spec assumption explicitly states that the diagnostic capability is used only for
local development and its removal is acceptable. If a diagnostic port is needed in the
future, it must be introduced as a separately secured feature.

Note: the G118 finding (line 96) is in the shutdown goroutine of `startPprofServer`:
`context.WithTimeout(context.Background(), 5*time.Second)`. Removing the function is
preferable to patching it with `context.WithoutCancel(ctx)` — the latter would leave
dead code in place and require explanation in every future code review.

### US3 — Integer overflow guards (G115 × 2)

**File 1**: `internal/store/idempotency_store.go:43` — `int64(h.Sum64())`

`pg_advisory_xact_lock` accepts any `bigint` (int64) value, including negative ones, so
a uint64 → int64 conversion that sets the sign bit does not cause a correctness failure.
However, gosec G115 flags the unchecked conversion, and FR-003 requires that overflow
conditions not produce silent incorrect results.

Fix: mask to non-negative int64 range before converting:
```go
return int64(h.Sum64() & math.MaxInt64)
```
The masking is deterministic — identical inputs still produce identical lock keys — so
concurrent callers for the same `(endpointID, key)` continue to acquire the same
advisory lock. The lock-key space shrinks from [MinInt64, MaxInt64] to [0, MaxInt64],
which remains collision-safe for the advisory-lock purpose. Add `import "math"`.

**File 2**: `internal/store/postgres.go:29` — `int32(cfg.MaxConns)`

`pgxpool.Config.MaxConns` is `int32`; `PoolConfig.MaxConns` is `int`. An operator-supplied
value above `math.MaxInt32` (2 147 483 647) would silently wrap. Fix: add an explicit
range check before the conversion and return an error if the value exceeds `math.MaxInt32`:
```go
if cfg.MaxConns > math.MaxInt32 {
    return nil, fmt.Errorf("MaxConns %d exceeds int32 range", cfg.MaxConns)
}
pgxCfg.MaxConns = int32(cfg.MaxConns)
```
Add `import "math"`. This satisfies FR-003 and FR-005 simultaneously.

### US4 — Go toolchain version bump (govulncheck)

**File**: `go.mod`

Change the `go` directive from `go 1.25.0` to `go 1.25.10`. This resolves all 18
reported CVEs (in `crypto/tls`, `crypto/x509`, `net/url`, `net/http`, `net`,

No `toolchain` directive is required: the existing go.mod has no `toolchain` line, the
bump is within the same minor series (1.25.x), and `go mod tidy` regenerates `go.sum`
correctly for the updated toolchain declaration.

**File**: `.github/workflows/ci.yml`

Update `go-version: "1.23"` to `go-version: "1.25"` in the `lint-and-test` job. The
declared toolchain version in go.mod (1.25) and the version used in CI (1.23) are
currently inconsistent — this fix resolves both issues simultaneously.

### US5 — Surface hash.Write errors (G104 × 2)

**File**: `internal/store/idempotency_store.go:41-42`

`hash.Hash.Write` implements `io.Writer` and its documentation states it never returns a
non-nil error. Gosec G104 flags implicit discard of error returns from `Write`-family
calls. FR-007 requires propagation, not just explicit discard — using `_, _` suppresses
the error rather than surfacing it to the caller. Fix: change `lockKey` to return
`(int64, error)` and check each `h.Write` return explicitly. `AcquireAdvisoryLock`
already returns `error` and chains naturally.

The combined `lockKey` and `AcquireAdvisoryLock` signatures after US3 + US5 fixes:
```go
func lockKey(endpointID uuid.UUID, key string) (int64, error) {
    h := fnv.New64a()
    if _, err := h.Write(endpointID[:]); err != nil {
        return 0, fmt.Errorf("lockKey write endpointID: %w", err)
    }
    if _, err := h.Write([]byte(key)); err != nil {
        return 0, fmt.Errorf("lockKey write key: %w", err)
    }
    return int64(h.Sum64() & math.MaxInt64), nil
}

func (s *IdempotencyTxStore) AcquireAdvisoryLock(...) error {
    key, err := lockKey(endpointID, idempotencyKey)
    if err != nil {
        return fmt.Errorf("advisory lock: %w", err)
    }
    _, err = s.tx.Exec(ctx, `SELECT pg_advisory_xact_lock($1)`, key)
    ...
}
```
`hash.Hash.Write` is documented to never fail; these error paths are reachable only if
the implementation is replaced. The error will surface to the event-submission caller,
which already handles `AcquireAdvisoryLock` errors.

### FR-010 — CI integration

**Makefile**: Add a `security-scan` target after the existing `lint` target:
```makefile
security-scan:
	gosec ./...
	govulncheck ./...
```

Both tools exit non-zero when findings are present, causing `make security-scan` to fail.
The target is not added to the default build chain; it is invoked explicitly in CI.

**`.github/workflows/ci.yml`**: Add a new parallel `security` job:
```yaml
security:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-go@v5
      with:
        go-version: "1.25"
        cache: true
    - name: Install security tools
      run: |
        go install github.com/securego/gosec/v2/cmd/gosec@v2.22.4
        go install golang.org/x/vuln/cmd/govulncheck@latest
    - name: gosec
      run: gosec ./...
    - name: govulncheck
      run: govulncheck ./...
```

The `security` job runs in parallel with `lint-and-test` (no dependency between them).
Pinning `gosec` to a specific version ensures reproducible builds; `govulncheck@latest`
is acceptable because it is the official Go tool and its behaviour is governed by the
vulnerability database, not by the tool version.

## Testing Strategy

- **Unit (retry.go)**: Table-driven test over `Delay(n)` for all valid n values —
  assert returned duration is within ±15% of the base schedule value; assert that 1 000
  successive calls produce no strictly monotonic sequence (non-predictable output). The
  existing `retry_test.go` covers schedule values; extend it for the jitter-range
  assertion. Test the error path by verifying the error return type and nil under normal
  conditions.
- **Unit (postgres.go)**: Test `NewPool` with `MaxConns > math.MaxInt32` — assert it
  returns a non-nil error. Existing pool-creation tests remain valid.
- **Unit (idempotency_store.go)**: Test `lockKey` with a known `(endpointID, key)` pair
  — assert the result is ≥ 0 (no negative values after the mask). Assert two distinct
  inputs produce distinct outputs (no unexpected collision from the masking).
- **Integration**: No new integration test scenarios are required beyond the existing
  suite. The acceptance scenarios for US2 (pprof paths return non-200) and US3 (distinct
  operations treated independently) are covered by existing tests.
- **Integration (SC-005)**: A new concurrent integration test will be added to
  `tests/integration/` — 100 goroutines each submitting 100 distinct `(endpointID, key)`
  pairs (10 000 total) against a real PostgreSQL instance via testcontainers-go. The test
  asserts that all 10 000 operations complete without any pair being treated as a
  duplicate, verifying FR-004 under concurrent load. This test runs under the existing
  `test-integration` Makefile target.
- **Scanner verification**: After all fixes are applied, run `gosec ./...` and
  `govulncheck ./...` locally and assert zero findings. This is the primary acceptance
  signal for SC-001, SC-002, SC-004.

## Trade-offs

| Decision | Chosen | Rejected | Reason |
|---|---|---|---|
| RNG source for jitter | `crypto/rand.Read` directly | `math/rand/v2` | FR-001 mandates a CSPRNG. `math/rand/v2` is a seeded PRNG — it satisfies gosec G404 but not FR-001's "cryptographically secure source" requirement. |
| `applyJitter` error handling | Change signature to return `error`; caller falls back to base delay | Panic on error; ignore error silently | FR-007 requires propagation, not suppression. Fallback preserves availability — since `crypto/rand.Read` cannot fail on Go ≥ 1.20, this path is dead code in practice but satisfies the spec contract. |
| pprof removal scope | Remove import + entire `startPprofServer` function + all `--pprof-addr` flags | Remove import only; keep `startPprofServer` serving empty mux | With the import removed, `startPprofServer` becomes dead code that starts an HTTP server serving 404 to everything. Removing it is cleaner, eliminates G118 without a patch, and matches the spec assumption that local diagnostic capability is acceptable to remove. |
| G118 fix | Removed with `startPprofServer` | Patch with `context.WithoutCancel(ctx)` | See above — removal is simpler and eliminates the finding rather than working around it. |
| uint64→int64 masking | `h.Sum64() & math.MaxInt64` | Leave negative values; use `//nolint` | Masking produces a valid and deterministic key in the non-negative int64 range. `//nolint` suppresses the tool instead of fixing the code, which would leave the finding unresolved in aggregate reports. |
| int→int32 range check | Explicit `> math.MaxInt32` guard + error return | `//nolint`; silent clamp to MaxInt32 | FR-003 requires surfacing the error. A silent clamp would mask a misconfiguration. |
| hash.Write error handling | Change `lockKey` to `(int64, error)`; propagate through `AcquireAdvisoryLock` | `_, _ = h.Write(…)` + comment | FR-007 requires propagation, not explicit discard. `AcquireAdvisoryLock` already returns `error`, so the chain adds no new noise. The error paths are dead code in practice but satisfy the FR contract for future-proofing. |
| govulncheck tool version | `@latest` | Pinned version | `govulncheck` is the official Go vulnerability tool; its findings are database-driven, not version-driven. Pinning the tool version does not protect against new CVE entries — only `go mod tidy` with a patched toolchain does. |
| gosec tool version | `v2.22.4` (pinned) | `@latest` | gosec rule changes can introduce new findings on unchanged code. Pinning prevents unexpected CI failures from rule updates. |
